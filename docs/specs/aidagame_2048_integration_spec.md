# 2048 — интеграция, интерфейс и критерии приёмки

**Дата:** 30 октября 2026. **Продукт:** Муроблоки, `aidagame`. **Этап:** следующий модуль после 1.2.0; 2048 реализована локально в 1.3.0.

**Статус:** согласовано; базовые параметры подтверждены, реализация разрешена пользователем. Публикация отдельно от реализации.

Этот документ расширяет [архитектурное ТЗ](ТЗ%20на%20техническую%20архитектуру,%20хранение%20данных.md) для 2048. Правила игры определяет [игровое ТЗ](aidagame_2048_gameplay_spec.md). Исторический объём 1.2.0 остаётся в [release-scope.md](../release-scope.md); исключение 2048 из того релиза не означает запрет отдельно согласовать следующий этап.

## 1. Объём

- Чистый движок 2048, поле 4×4, свайпы/клавиатура, анимации, независимые партия и рекорд.
- Подключение второй игры к каталогу, общей навигации, результатам, настройкам, сохранениям и JSON-копии.
- Совместимая миграция действующих данных 1010!, проверка конфликтов вкладок, отказов записи и полного импорта.
- Числовые плитки без рисунков во всех состояниях, шесть тем × два режима.
- Сохранение исправленного общего контейнера, PWA, base `/aidagame/`, существующих правил и палитр 1010!.

Не входят: сервер, аккаунты, идентификация устройства, синхронизация, накопленная статистика, Tap Match, отмена, подсказки, экранные стрелки и окно победы на 2048. Публикация будущего релиза требует отдельного разрешения; подготовка документации его не даёт.

## 2. Текущее состояние и необходимое расширение

До этапа 1.3.0 типы, репозиторий и оболочка поддерживали только 1010!. В 1.3.0 они расширены типизированной картой двух игр, независимыми партиями/рекордами и отдельным компонентом 2048; результат 2048 не содержит счётчик линий.

Агент расширяет эти границы минимально, без нового стека, второй базы и переписывания движка 1010!. Переиспользуются Vue 3, Vite, TypeScript, существующие idb и PWA. Новые крупные зависимости для 2048 не нужны.

## 3. Модуль и оболочка

- Стабильный `gameId`: `2048`; существующий `block-puzzle` не переименовывается.
- Контракт: `id`, `name`, `load`, `createInitialState`, `getStatus`, `validateSave`, `saveVersion`. Тип состояния привязан к gameId; числовые плитки не типизируются как Group/Shape 1010!.
- `load` загружает реальный компонент 2048 лениво. Карточка становится активной при готовой реализации и пройденной приёмке; документы сами по себе её не активируют.
- Оболочка знает выбранную игру и независимые данные обеих игр. Переключение экранов/игр не создаёт новую партию и не меняет чужой рекорд.
- Общие статусы: `not_started`, `active`, `completed`. Фазы `moving`/`resolving` остаются временными состояниями UI, не записываются в БД.
- Результаты 2048 показывают счёт и рекорд; строка «линий очищено» принадлежит только 1010!. Дополнительная статистика результата в этот этап не добавляется.
- Кнопки общей оболочки остаются «Вернуться» и «Заново». Подтверждённый перезапуск затрагивает только выбранную партию и сохраняет её рекорд.

## 4. Движок и данные для анимаций

Предлагаемые файловые зоны: `src/games/2048/` для логики, типов, компонента и оформления; общие registry/storage/App расширяются на местах. Это ориентир ответственности, а не требование переносить все существующие файлы 1010!.

- Канонический `board` — 16 чисел по строкам, индекс `row * 4 + col`. Обработка линии общая для четырёх направлений.
- Чистая операция возвращает новое состояние и метаданные: `changed`, `scoreDelta`, перемещения `from/to/value`, пары слияния и их результат, новую плитку `index/value`, признак завершения. Все метаданные относятся к одной операции, а не запускают новые ходы событиями UI.
- Результат движения до генерации тестируется отдельно. После изменившего поле хода rng вызывается только для одной новой плитки; при старте — для двух последовательных созданий, при неизменившем поле ходе — ни разу.
- Для воспроизводимости документировать порядок вызовов rng в реализации. Свободные позиции перечисляются в стабильном порядке; позиция выбирается равномерно, значение 2/4 — независимо.
- Визуальная идентичность плиток и карта слияний живут в памяти. Нельзя анимировать движение только заменой текста в фиксированных клетках или определять слияния по DOM/цветам.
- Перемещение начинается с 120 мс; эффекты слияния/появления короткие, без искусственного ожидания после завершения. Reduced-motion убирает/сокращает фазы и освобождает ввод.
- Отмена анимации, уход в меню/настройки, скрытие вкладки и размонтирование не повторяют ход и не оставляют ввод заблокированным. Экран результата появляется после завершения визуальной операции; запись при этом может завершиться успехом либо явной ошибкой.

## 5. Канонический снимок и отдельные рекорды

Первый формат состояния 2048:

```ts
type State2048 = {
  version: 1;
  status: 'active' | 'completed';
  board: number[]; // ровно 16, порядок строк
  score: number;
  moves: number;   // только изменившие поле ходы
};
```

`gameId` — ключ общего контейнера игры; `saveVersion: 1` — метаданные формата в нём. `version` внутри State2048 обозначает версию его структуры и согласуется с валидатором. Общий `revision` — инфраструктурные данные, не поле плитки. `best` хранится отдельно и не дублируется как источник истины внутри State2048.

Валидатор проверяет известную версию, форму и числа поля, минимум две непустые плитки в завершённом снимке хода, неотрицательные безопасные целые score/moves, согласованность статуса и возможности хода. Пустой массив/полностью пустое поле не являются активной сохранённой партией. `canMove` не объявляет пустую доску играбельной лишь из-за пустых клеток.

Рекорд 2048 — независимое неотрицательное безопасное целое, не меньше текущего score. Новая партия/проигрыш его не сбрасывают. При полном импорте восстанавливается значение файла, даже меньшее прежнего локального рекорда.

## 6. Хранение, миграция и ошибки

- Сохранить имя базы `muroblocks-v1`, действующие ключи `game:block-puzzle`, `app:settings` и данные 1010!.
- Использовать существующие `items`, `records`, `metadata`. Для второй игры предусмотрены `items['game:2048']` и `records['2048']`. Добавление ключей само по себе не требует изменения физической версии IndexedDB; повышение версии обязательно только при изменении схемы stores/indexes.
- Общий снимок приложения содержит данные обеих игр и отдельные рекорды. Изменение TypeScript-типа не заменяет миграцию прежних сохранённых данных.
- Миграция прежних IndexedDB/localStorage/JSON сохраняет 1010!, настройки, рисунок и рекорд. 2048 остаётся не начатой (`save: null`, `best: 0`), без вызова rng и записи выдуманной партии.
- Миграции валидируются, идемпотентны и не удаляют оригиналы при отказе. Разные прежние копии не сравниваются по принципу «больше счёт — свежее».
- Проверка ожидаемой общей ревизии и запись происходят в одной транзакции. Партия, изменившийся рекорд и метаданные согласованы; остальные данные приложения сохраняются. BroadcastChannel — уведомление, не замена проверке ревизии.
- Данные в памяти обновляются результатом одной игровой операции, а не событием каждого кадра. Успех хранения подтверждается только после tx.done. При отказе актуальный согласованный снимок остаётся в памяти с предупреждением, повтором и экспортом. Повтор записи не считает ход заново.
- При конфликте вкладка прекращает запись и предлагает экспорт своей версии или явную загрузку свежей. Без BroadcastChannel защита остаётся действующей.
- Повреждение партии одного модуля не даёт права удалить данные/рекорд другого. Восстановление повреждённой партии требует явного действия, сохраняет читаемый отдельный рекорд и предоставляет исходные данные для диагностики.

## 7. Общий JSON: точное полное восстановление

Сохранить appId `muroblocks`. Существующий контейнер `exportVersion: 2` уже имеет карту games; её расширение на второй известный модуль не требует автоматически формата v3. Если при реализации изменится сама структура контейнера, требуется отдельная версия и миграция, а не молчаливая несовместимость.

После реализации новый экспорт содержит:

```text
appId: muroblocks
exportVersion: 2
exportedAt
settings
 games.block-puzzle: saveVersion, save, records.best
 games.2048:         saveVersion, save, records.best
```

Для не начатой реализованной игры `save` равен null. Копия включает общие настройки и рекорды обеих игр, а не только открытый модуль. Состояние из памяти при отказе БД помечается пользовательским сообщением; приложение не утверждает, что файл уже сохранён вне устройства.

Импорт принимает прежний JSON v1 и известный v2 только с 1010!, а также v2 с двумя реализованными играми. Неизвестный gameId/будущая неподдерживаемая версия или любое повреждение отклоняют весь файл до записи. Прежний клиент, не поддерживающий 2048, может безопасно отклонять новую копию.

Полное восстановление — без объединения и без выбора максимального рекорда:

1. Прочитать, проверить и мигрировать весь файл в памяти.
2. Известная игра, отсутствующая в старой копии, получает `save: null`, `best: 0`.
3. Предпросмотр показывает дату, наличие/отсутствие обеих игр, статус, счёт, рекорд. Если локальные данные 2048 будут сброшены из-за их отсутствия в файле — прямо предупредить об этом до подтверждения. Если 2048 ещё не начиналась, не утверждать, что существующая партия будет потеряна.
4. После подтверждения одной транзакцией заменить обе партии, настройки и рекорды с проверкой ревизии.
5. Отмена, повреждение, неподдерживаемый формат, конфликт и отказ любой записи сохраняют прежние данные обеих игр.

Кнопки остаются внизу общих настроек, работают офлайн. Отдельных серверных кнопок/страниц не добавлять.

## 8. Оформление без рисунков

- Темы и режим общие: 6 × 2. Агент самостоятельно подбирает числовую палитру в существующем стиле и проверяет её по всем 12 вариантам; дополнительное согласование каждого HEX не требуется.
- Цвет определяется числом и активной темой. Подготовить таблицу/детерминированный resolver для 2–2048, больших значений и безопасного продолжения палитры. Пять категорий фигур 1010! не считаются готовой палитрой 2048. Цвета 1010! не менять.
- Цифра всегда полностью видна, включая длинные значения: без обрезания, многоточия и экспоненциальной записи. Размер шрифта адаптируется к длине, не меняя размеры клетки. Проверять контраст с фактическим фоном в каждом режиме.
- Рисунков нет на поле, при движении, слиянии, появлении и в превью 2048. Не передавать stamp/pattern в renderer 2048 и не применять CSS-mask к числовым плиткам. Общие логотип/иконки оболочки при этом допустимы.
- Общий раздел называется «Рисунок блоков 1010!»; выбор сохраняется для 1010! и не воздействует на 2048. Не очищать pattern при смене игры или импорте партии 2048.
- Числовые плитки и 16 фоновых клеток разделены. Не переиспользовать глобальную сетку repeat(10) как 4×4: стили поля 2048 изолированы от 1010!.
- Сохранить общий контейнер всех экранов, выравнивание шапки/поля/кнопок, пропорциональные скругления квадратов. Нет ResizeObserver-цикла, постепенного уменьшения, сдвига влево или масштабирования поля при свайпе. На коротком landscape допустима прокрутка вместо сжатия поля.

## 9. Ввод и жизненный цикл

- Сенсорный указатель: один основной pointer, захват на поле, смещение от pointerdown до pointerup. max(abs(dx), abs(dy)) не меньше 24 CSS px; равенство осей отменяет неоднозначный диагональный жест.
- Команда выполняется только на pointerup. Второй палец, pointercancel, потеря захвата до завершения, blur, скрытие приложения и смена ориентации отменяют текущий жест. Нельзя одновременно подписать pointerup и touchend так, чтобы один жест создавал два хода.
- На поле `touch-action: none`; вне него сохраняется прокрутка одним пальцем. Общие guards против щипка/выделения сохраняются и не заменяются более широким разрешением системных жестов.
- Стрелки клавиатуры обрабатываются только в активной 2048 без модального диалога, не прокручивают страницу. event.repeat игнорируется; при обработке хода нет буфера следующей команды. На других экранах обработчик отсоединён/неактивен.
- Отмена жеста не отменяет уже принятую чистую логическую операцию; при перезагрузке восстанавливается последний подтверждённый снимок без дополнительного spawn и проигрывания хода.

## 10. PWA, производительность, порядок реализации

- Сохранить GitHub Pages base/scope/start_url `/aidagame/`, кэширование lazy chunk 2048 и её стилей. Первый запуск и продолжение игры, настройки и общий экспорт/импорт работают офлайн после готовности кэша.
- Обновление PWA не прерывает свайп, ход, импорт или несохранённые данные. Проверить переход с текущей опубликованной 1.2.0, а не только с исходной версии 1010!.
- Сохранить бюджеты приложения: все JS/CSS ≤150 КиБ gzip, обязательный precache ≤1 МиБ. Сравнить production до/после и явно указать профиль/ограничения измерений, отдельно ручную проверку физического iPhone.
- Агент формулирует задачи сам: проверки исходной 1010! → движок 2048 → расширение хранения/миграций → подключение оболочки → числовые темы/ввод/анимации → браузерная приёмка/PWA/производительность → матрица результатов. Публикация отдельно от реализации.
