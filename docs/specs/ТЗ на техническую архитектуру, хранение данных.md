## 1. Назначение документа

Документ определяет техническую реализацию приложения «Муроблоки».

Он устанавливает:

- Технологический стек.
- Архитектуру общей оболочки.
- Принципы подключения игровых модулей.
- Управление состоянием приложения.
- Структуру и жизненный цикл игровых сохранений.
- Ручной экспорт и атомарный импорт прогресса через JSON-файл.
- Технические требования к PWA.
- Границы отложенного серверного резервирования, не входящего в ближайший релиз.
- Требования к безопасности, производительности и качеству.
- Порядок сборки, публикации и обновления.

Документ не переопределяет игровые механики, пользовательские сценарии и визуальный дизайн.

### 1.1. Связанные документы

При разработке использовать:

1. «Муроблоки — ТЗ на экраны и вайрфреймы».

В случае противоречий не менять требования самостоятельно. Проблему необходимо зафиксировать и согласовать.

## 2. Продуктовая и техническая модель

«Муроблоки» — общедоступное приложение с независимыми казуальными головоломками.

Пользователь открывает сайт в браузере либо устанавливает его на главный экран смартфона как PWA.

### 2.1. Принципы

- Приложение доступно без обязательной регистрации.
- Публичный доступ к игровому коду и интерфейсу разрешён.
- Каждому устройству доступен собственный локальный прогресс.
- Для игрового процесса не требуется постоянное подключение к серверу.
- Разные игровые модули имеют независимые партии и рекорды.
- Общие настройки оформления используются на уровне приложения.
- Потеря сетевого соединения не должна прерывать активную игру.
- Новые игровые модули подключаются без существенной переработки существующих.

### 2.2. Состав игровых модулей

Предусмотреть архитектуру для:

- `block-puzzle` — головоломка с размещением фигур.
- `2048` — головоломка с объединением числовых плиток.
- `tap-match` — будущая головоломка на сопоставление элементов.

**2048 отдельно согласована и реализована локально в 1.3.0; её правила и интеграция задаются отдельными ТЗ. Tap Match остаётся вне текущего объёма.**

Первым полностью реализуемым модулем является Block Puzzle.

Общая оболочка должна поддерживать каталог игр, независимо от количества готовых модулей.

В продуктовой версии не должны запускаться неготовые игры или экраны с имитацией игрового процесса.

## 3. Технологический стек

### 3.1. Клиентское приложение

Согласованный стек ближайшего релиза:

| Компонент | Технология |
| --- | --- |
| Язык | TypeScript |
| Сборка | Vite |
| UI-компоненты | Vue 3, компоненты Single File Components |
| Стили | CSS с переменными и дизайн-токенами |
| PWA | vite-plugin-pwa |
| Локальная база | IndexedDB |
| Доступ к IndexedDB | idb или аналогичная лёгкая библиотека |
| Тесты логики | Vitest |
| E2E-тесты | Playwright |
| Контроль версий | Git |

Vue 3 + Vite + TypeScript согласованы. Существующие чистые модули игровой логики переносятся без переписывания правил; типизация не должна менять поведение. Vite и TypeScript относятся к инструментам разработки/сборки. В браузер поступает production JavaScript и CSS; Node.js на хостинге игры не требуется. Проверка типов запускается отдельно от сборки.

Не использовать Next.js, SSR и серверный рендеринг без обоснованной необходимости.

Для первой версии приложение может полностью работать на стороне клиента.

### 3.2. Отрисовка игровых полей

Для Block Puzzle предпочтительно использовать DOM/CSS Grid и Pointer Events.

Причины:

- Поле состоит из небольшого количества дискретных клеток.
- Не требуется физический движок.
- Анимации достаточно простые.
- Можно напрямую применять CSS-темы.
- Удобнее управлять адаптивностью и состояниями элементов.

Canvas допускается, если испытания покажут существенные преимущества.

Технология отрисовки не должна влиять на правила игры.

Другие игровые модули могут использовать иной способ отображения, если это требуется их механикой.

### 3.3. Серверный компонент — отложенный объём

В ближайшем релизе сервер отсутствует. API, SQLite, Docker volume, VPS, Coolify, аккаунты, коды восстановления и автоматическая серверная отправка не реализуются. Резервное копирование выполняется пользователем через экспорт JSON-файла. Разделы 9 и 10 сохраняют направление возможного будущего серверного этапа и не являются условиями приёмки текущего релиза. Не создавать пустые серверные модули или неработающие элементы интерфейса.

## 4. Архитектура приложения

### 4.1. Разделение ответственности

Приложение состоит из трёх основных частей.

**Application Shell**

Отвечает за:

- Главное меню.
- Каталог головоломок.
- Навигацию.
- Общие настройки.
- Применение дизайн-токенов.
- Общие диалоги.
- Управление PWA.
- Сервис сохранений и резервных копий.

**Игровые модули**

Каждый игровой модуль отвечает за:

- Собственные правила.
- Собственное состояние партии.
- Проверку игровых действий.
- Статистику текущей партии.
- Рекорд, сохраняемый отдельно от партии.
- События игрового процесса.
- Подготовку данных сохранения.

**Инфраструктурный слой**

Отвечает за:

- Доступ к IndexedDB.
- Экспорт и импорт JSON.
- Общие операции ручного экспорта и атомарного импорта JSON.
- Обработку ошибок хранения.
- Версионирование и миграции.
- Обновления PWA.

### 4.2. Структура проекта и перенос

Разделить оболочку, экраны, компоненты Block Puzzle, чистые правила, темы и инфраструктуру хранения. В корне сохраняются `AGENTS.md`, `docs/`, конфигурация Vite/TypeScript, package-файлы и `.github/workflows/`.

Рекомендуемые зоны: `src/app/`, `src/screens/`, `src/games/block-puzzle/`, `src/shared/storage/`, `src/shared/backup/`, `src/design/`, `tests/`. Это зоны ответственности, а не требование создавать все папки заранее. Допустим постепенный перенос из существующих `src/game/` и `src/storage/`.

Статические ресурсы обрабатываются Vite или размещаются в `public/` с учётом `base`. Конкретный способ выбирается по результатам проверки существующих SVG/CSS-масок. Нельзя терять `.github`, оригинальные ТЗ и изображения. Рабочая сборка находится в `dist/`; этот каталог генерируется и не заменяет исходники.

При переносе сохраняются бренд «Муроблоки», идентификаторы игр/тем/рисунков и действующие данные. Новая структура разрешена только в рамках согласованного перехода; переписывание игровых правил не требуется.

## 5. Контракт игрового модуля

Приложение должно подключать игровые модули через минимальный общий контракт.

### 5.1. Обязательные сведения

Каждый модуль предоставляет:

- `id` — уникальный постоянный идентификатор.
- `name` — название.
- `load` — способ загрузки экрана игры.
- `createInitialState` — создание начального состояния.
- `getStatus` — получение состояния партии для общего меню.
- `validateSave` — проверка корректности сохранения.
- `saveVersion` — версия формата игровых данных.

Дополнительные методы определяются потребностями конкретной игры.

### 5.2. Статусы партии

Общее приложение использует:

- `not_started` — партия отсутствует.
- `active` — партия доступна для продолжения.
- `completed` — партия закончена.

Внутренние состояния вроде перетаскивания, обработки очистки или анимации остаются внутри игрового модуля.

### 5.3. Изоляция модулей

Запрещается:

- Использовать единое состояние поля для всех игр.
- Включать правила Block Puzzle в общую оболочку.
- Привязывать общие настройки к одному игровому модулю.
- Использовать одинаковые ключи сохранений для разных головоломок.

Общие сервисы не должны знать, как устроены внутренние игровые правила.

### 5.4. Подключение новой игры

Для добавления новой головоломки должно быть достаточно:

1. Создать модуль игры.
2. Реализовать его правила и интерфейс.
3. Определить формат сохранения.
4. Зарегистрировать модуль в каталоге.
5. Добавить необходимые тесты.

Добавление модуля не должно требовать изменения правил уже существующих игр.

## 6. Управление состоянием

### 6.1. Уровни состояния

Разделить данные на три категории.

**Общее состояние приложения:**

- Активная цветовая тема.
- Выбранные настройки оформления.
- Текущий экран.
- Состояние общих диалогов.

**Состояние игрового модуля:**

- Текущая партия.
- Счёт.
- Рекорд.
- Статистика только текущей партии; накопленные счётчики всех партий отложены.
- Игровые данные.

**Состояние инфраструктуры:**

- Состояние локального сохранения.
- Состояние экспорта, импорта и миграции.
- Ожидаемую ревизию данных и конфликт вкладок.
- Наличие ошибок восстановления.

### 6.2. Требования

- Возврат в меню не сбрасывает игровую партию.
- Смена темы не перезаписывает игровые данные.
- Открытие другого игрового модуля не удаляет предыдущие сохранения.
- Новая партия сбрасывает только данные соответствующей игры.
- Рекорд сохраняется отдельно от текущей партии.
- Временное состояние взаимодействия не обязано сохраняться.

Например, положение фигуры в процессе незавершённого перетаскивания не записывается.

## 7. Локальное хранение данных

### 7.1. Основное хранилище

Использовать IndexedDB.

Локальная база должна хранить прогресс непосредственно на устройстве пользователя.

Не использовать localStorage как основной источник истины для игрового прогресса.

### 7.2. Логическая структура

Предусмотреть хранилища:

| Хранилище | Содержание |
| --- | --- |
| `settings` | Общие настройки приложения |
| `gameSaves` | Снимки состояния партий |
| `gameRecords` | Отдельный рекорд каждой игры; накопленные счётчики отложены |
| `backupMetadata` | Служебные данные ручного восстановления, если они нужны реализации; без серверных секретов |
| `metadata` | Версия схемы и технические данные |

Это логические области, а не обязательные имена object store. В релизе 1.2.0 физическая база `muroblocks-v1` версии 2 сохраняет `items` (ключи `app:settings`, `game:block-puzzle`), добавляет `records` (ключ `block-puzzle`) и `metadata` (общая `revision`). `backupMetadata` отдельно не создаётся: серверных копий нет, импорт выполняется одной транзакцией. Каждая запись игровых данных связана с `gameId`.

### 7.3. Настройки приложения

В 1.3.0 без повышения версии базы добавлены `items["game:2048"]` и `records["2048"]`; одна общая ревизия охватывает обе игры. Формат 1010! сохранён, проверен откат на 1.2.0 и повторное обновление.

Пример логической структуры будущего расширения (не физический формат релиза 1.2.0):

```json
{
  "schemaVersion": 1,
  "themeId": "pastel",
  "mode": "light",
  "gameAppearance": {
    "block-puzzle": {
      "patternId": "none"
    }
  }
}
```

Фактический совместимый формат настроек 1.2.0: `{ "theme": "pastel", "mode": "light", "pattern": "none" }`. Версия схемы хранится в версии IndexedDB, а не добавляется в прежний объект настроек. Миграция сохраняет прежние ID.

Цветовая тема является общей для приложения.

Рисунки блоков относятся к конкретному игровому модулю, поскольку другие головоломки могут не поддерживать аналогичное оформление.

Шесть тем: Пастель, Зима, Весна, Лето, Осень, Ай Да Настя. У каждой есть светлый и тёмный режим; режим сохраняется отдельно от темы. Рисунки: Однотонный, Лапка, Снежинка, Сердечки, Лист, Тыковка. Существующие внутренние ID сохраняются (`none`, `paw`, `snow`, `heart`, `leaf`, `pumpkin`); переименование подписей не создаёт новый формат прогресса.

### 7.4. Сохранение партии

Пример структуры:

```json
{
  "gameId": "block-puzzle",
  "schemaVersion": 1,
  "status": "active",
  "revision": 12,
  "updatedAt": "2026-10-29T12:00:00Z",
  "state": {
    "board": [],
    "availableShapes": [],
    "score": 240,
    "clearedLines": 8
  }
}
```

Содержимое `state` определяется конкретным игровым модулем.

Для Block Puzzle внутри состояния необходимо хранить сведения о визуальной группе занятых клеток.

Не сохранять HEX-цвет каждой клетки. Цвет вычисляется по идентификатору группы и активной теме.

### 7.5. Рекорды и границы статистики

Хранить рекорд отдельно от текущей партии с привязкой к `gameId`. Новая партия и проигрыш не обнуляют рекорд. Обновление снимка партии и рекорда при завершении хода выполняется согласованно.

Накопленные счётчики всех партий и экран статистики отложены. Поля текущей партии `turns`, `clearedLines`, `score` сохраняются: они уже существуют и нужны для совместимости и результата партии. Историю прошлых партий не выдумывать.

При миграции извлечь действующий `best` из старого снимка в отдельную запись рекорда. Обычная новая партия сохраняет прежний рекорд; подтверждённый импорт восстанавливает рекорд из файла, даже если он меньше локального. Общие настройки и данные других игр не меняются при перезапуске одной партии.

### 7.6. Момент автосохранения

Сохранение выполняется:

- После каждого успешно завершённого хода.
- После изменения настроек.
- После окончания партии.
- После подтверждённого начала новой партии.
- После изменения отдельного рекорда соответствующей игры.

Состояние должно сохраняться как согласованный снимок.

Нельзя записывать частично завершённый ход, при котором поле уже изменилось, но очки или доступные фигуры ещё не обновлены.

### 7.7. Атомарность

Операции сохранения взаимосвязанных данных должны использовать транзакции IndexedDB.

При ошибке записи не должно возникать частично сохранённого состояния.

Если запись не удалась:

1. Не сообщать пользователю об успешном сохранении.
2. Сохранить актуальное состояние в памяти, пока приложение открыто.
3. Показать ненавязчивое предупреждение.
4. Предложить повторную попытку и экспорт актуального согласованного снимка из памяти, если это возможно.
5. Вернуть вызывающему коду достоверный результат операции; не скрывать отказ записи за успешным завершением Promise.
6. Не создавать два несогласованных источника истины: старые данные localStorage поддерживаются миграцией, а политика временного отказа IndexedDB фиксируется и проверяется тестами.

### 7.8. Несколько вкладок

Предусмотреть защиту от конфликтов при открытии одного приложения в нескольких вкладках.

Обязательно:

- Использовать ревизии и проверять ожидаемую ревизию внутри той же транзакции, что выполняет запись.
- Предотвращать тихую перезапись более свежего состояния старым, включая импорт и новую партию.
- Уведомлять другие вкладки через BroadcastChannel, если API доступен; корректность записи не должна зависеть только от уведомлений.
- При конфликте сохранить несохранённое состояние в памяти, остановить конфликтующие записи, предложить загрузить актуальные данные либо экспортировать локальную версию.
- Обработать открытые старые соединения и `versionchange`/`blocked` при миграции схемы.

Если текущая вкладка обнаружила более новую версию партии, нельзя незаметно заменить её собственным устаревшим состоянием.

### 7.9. Устойчивость хранения

При поддержке браузером допускается запрос постоянного хранения через `navigator.storage.persist()`.

Успех запроса нельзя считать гарантированным.

Данные могут быть потеряны при удалении приложения, очистке хранилища или отдельных действиях системы.

**Локальное хранение не является резервным копированием.**

### 7.10. Совместимость действующей версии

Поддержать данные `muroblocks-v1`, object store `items`, ключи `game:block-puzzle` и `app:settings`, а также прежний fallback localStorage с такими же ключами и префиксом базы. Поддержать старый снимок партии `version: 1` и прежние настройки `theme`, `mode`, `pattern`.

Не менять имя базы и не удалять старые записи вместо миграции. Разделить версию базы, версию игровых данных и версию JSON-экспорта. Миграция идемпотентна: повторное открытие не дублирует и не обнуляет данные. При ошибке откатить изменения; неизвестную более новую схему не перезаписывать. При наличии разных копий в старых IndexedDB/localStorage не угадывать свежесть по счёту: приоритет и безопасное разрешение неоднозначности проверяются до записи.

До внедрения новой схемы подготовить фикстуры реальных форматов v1 и тесты: активная/завершённая партия, рекорд, настройки, fallback, повреждение, повторный запуск миграции и две открытые вкладки.

## 8. Экспорт и импорт сохранений

Экспорт и импорт являются обязательными общими функциями приложения.

Они должны охватывать данные всех реализованных игровых модулей (с 1.3.0 — Block Puzzle и 2048), настройки и отдельные рекорды. Для реализованной, ещё не начатой 2048 экспорт содержит `save: null`, `best: 0`; выдуманной партии нет. Нереализованная Tap Match не создаёт сохранения. Внизу страницы настроек разместить раздел «Сохранения» с кнопками «Экспорт сохранений» и «Импорт сохранений».

### 8.1. Экспорт

Пользователь может вручную скачать резервную копию в формате JSON.

Рекомендуемое имя:

`muroblocks-backup-YYYY-MM-DD.json`

Файл содержит:

- Идентификатор приложения.
- Версию формата экспорта.
- Дату создания.
- Общие настройки.
- Состояния партий.
- Отдельные рекорды доступных игр и статистику внутри текущих партий. Накопленные счётчики прошлых партий в этом релизе отсутствуют.

Пример внешней структуры:

```json
{
  "appId": "muroblocks",
  "exportVersion": 2,
  "exportedAt": "2026-10-29T12:00:00Z",
  "settings": {},
  "games": {
    "block-puzzle": {
      "saveVersion": 1,
      "save": {},
      "records": {}
    }
  }
}
```

Это пример нового контейнера экспорта версии 2, а не окончательная модель конкретного игрового состояния. Экспорт создаёт согласованный снимок всех данных одной ревизии. В обычном режиме он читает подтверждённые данные; при отказе хранения отдельно сообщает, что экспортируется актуальное состояние из памяти. Скачивание файла не означает запись на сервер и не гарантирует, что пользователь сохранил файл вне устройства.

### 8.2. Исключения из экспорта

В файл не включать:

- Секретный код доступа к серверной копии.
- Серверные ключи.
- Внутренние токены.
- Служебные данные установки, не необходимые для восстановления.
- Чувствительные конфигурационные параметры инфраструктуры.

### 8.3. Импорт

При выборе файла приложение должно:

1. Прочитать файл.
2. Проверить его формат.
3. Проверить идентификатор приложения.
4. Проверить поддерживаемую версию экспорта.
5. Проверить данные каждого игрового модуля.
6. Показать, какие данные будут восстановлены.
7. Предупредить о замене существующих сохранений.
8. Запросить подтверждение.
9. Выполнить восстановление согласованно, без частичной записи.

Не перезаписывать текущий прогресс без явного подтверждения пользователя. Подтверждённый импорт — полная замена поддерживаемых данных приложения содержимым файла: партии, настройки и отдельные рекорды. Не объединять партии и не сохранять автоматически больший локальный рекорд. Технические ревизии/метаданные согласовать заново; они не переносятся как блокировка с чужого устройства.

Перед подтверждением показать дату копии, поддерживаемые игры, состояние партии, счёт и рекорд; явно предупредить об их замене. Отмена, неподходящий файл или ошибка до/во время транзакции оставляют прежние данные без изменений. Весь файл валидируется и мигрируется до единой транзакции записи. Импорт учитывает изменение ревизии другой вкладкой между предварительным просмотром и подтверждением.

Перед импортом желательно автоматически подготовить резервную копию текущего состояния, доступную для восстановления.

### 8.4. Ошибки импорта

Обрабатывать:

- Неподходящий файл.
- Повреждённый JSON.
- Неизвестное приложение.
- Неподдерживаемую версию сохранения.
- Некорректные игровые данные.
- Ошибку записи в IndexedDB.

При ошибке существующие корректные сохранения должны остаться нетронутыми.

### 8.5. Совместимость

Новые версии приложения должны поддерживать миграцию известных старых схем сохранения. Обязательно читать прежний JSON `{format: "muroblocks-backup", version: 1, date, game, settings}` и новый контейнер `{appId: "muroblocks", exportVersion: 2, ...}`. Старый `game.best` преобразуется в отдельный рекорд; идентификатор `muroblocks` сохраняется для совместимости.

Неизвестные более новые версии нельзя загружать с попыткой угадать их структуру.

Если миграция невозможна, необходимо безопасно отказаться от импорта и объяснить причину.

## 9. Серверное резервное копирование — отложено

> Весь раздел 9 — возможное будущее направление. Не реализуется, не отображается в интерфейсе и не входит в критерии ближайшего релиза на GitHub Pages. Возврат к нему требует отдельного решения об инфраструктуре и API.

**Назначение:** восстановление прогресса после удаления установленного PWA, повреждения устройства или потери локальных данных.

Серверное резервирование не заменяет локальное хранение и не является обязательным для начала игры.

### 9.1. Принцип работы

Пользователь играет без регистрации.

При желании он включает резервное копирование в настройках.

Приложение создаёт отдельную запись резервной копии на сервере и выдаёт секретный код восстановления.

Пользователь сохраняет код вне приложения.

После включения:

- Основной игровой прогресс остаётся в IndexedDB.
- При наличии интернета приложение отправляет обновлённый снимок данных на сервер.
- Если интернет отсутствует, игра продолжает работать локально.
- При возвращении интернета приложение пытается передать актуальные изменения.

### 9.2. Код восстановления

Код является секретом, подтверждающим право доступа к конкретной резервной копии.

Требования:

- Генерируется криптографически стойким способом.
- Не создаётся из имени пользователя, даты или простого числа.
- Имеет достаточную случайность — не менее 128 бит.
- Используется для чтения и обновления только своей записи.
- Не хранится на сервере в открытом виде.
- Не включается в URL.
- Не попадает в журналы запросов.
- Передаётся только через HTTPS.
- Не включается в обычный JSON-экспорт.

На сервере хранить производный проверочный идентификатор или хеш секретного кода.

При утере кода без сохранившейся авторизованной установки восстановление серверной копии не гарантируется.

### 9.3. Состав серверной записи

Предусмотреть:

- Уникальный ID резервной копии.
- Проверочный хеш секретного кода.
- Версию схемы.
- Ревизию данных.
- Дату создания.
- Дату последнего изменения.
- JSON-снимок прогресса.
- Служебную информацию для предотвращения конфликтов.

Не собирать имена, телефоны и email игроков для работы резервного копирования.

### 9.4. API

Предусмотреть минимальные операции:

**Создание резервной копии**

- Создать запись.
- Сформировать секрет восстановления.
- Вернуть информацию для сохранения на устройстве.

**Получение копии**

- Проверить секрет.
- Вернуть сохранённые данные и текущую ревизию.

**Обновление копии**

- Проверить секрет.
- Проверить ожидаемую ревизию.
- Валидировать формат данных.
- Сохранить новое состояние.

**Удаление копии**

- Проверить секрет.
- Удалить связанные данные по явному запросу пользователя.

Конкретные HTTP-маршруты и формат запросов зафиксировать в API-контракте перед реализацией.

### 9.5. Автоматическая отправка

Отправлять копию после изменений локальных данных с небольшой задержкой, объединяющей несколько последовательных операций.

Не создавать отдельный сетевой запрос на каждый кадр, движение фигуры или промежуточную анимацию.

Допустимая стратегия:

- Сохранить ход локально немедленно.
- Отметить данные как требующие резервирования.
- Через небольшую задержку попытаться передать актуальный снимок.
- При ошибке сети повторить попытку позже.

Резервирование не должно блокировать игровой процесс.

### 9.6. Состояние резервного копирования

Приложение должно различать:

- `disabled` — резервирование не включено.
- `pending` — есть локальные изменения, ещё не отправленные на сервер.
- `syncing` — выполняется отправка.
- `backed_up` — последняя копия успешно сохранена.
- `error` — ошибка соединения или сервера.
- `conflict` — обнаружено несовпадение ревизий.

Нельзя показывать «Прогресс сохранён на сервере», если последний запрос завершился ошибкой.

### 9.7. Восстановление

При вводе кода восстановления:

1. Проверить наличие соединения.
2. Выполнить запрос к серверу.
3. Проверить полученные данные.
4. Показать информацию о доступной копии.
5. Предупредить о возможной замене локального прогресса.
6. Запросить подтверждение.
7. Восстановить данные в IndexedDB.
8. Обновить приложение без потери восстановленных данных.

После успешного восстановления пользователь может продолжить игру с последнего успешно зарезервированного состояния.

### 9.8. Несколько устройств

**В этой версии резервное копирование не является полноценной синхронизацией нескольких устройств.**

Предполагается один основной источник изменений для одной серверной копии.

Если два устройства используют один код и пытаются обновлять одну копию, сервер должен предотвращать тихую перезапись более новых данных устаревшими.

Для этого использовать контроль ревизий.

При конфликте:

- Остановить автоматическую перезапись.
- Сообщить пользователю.
- Сохранить локальные данные обоих устройств.
- Не объединять игровые партии автоматически.
- Предложить явное восстановление или выбор версии после согласования соответствующего интерфейса.

Полноценная двусторонняя синхронизация не входит в текущую версию.

### 9.9. Ограничения

Код восстановления фактически является ключом доступа к сохранению.

Если он станет известен постороннему, тот потенциально сможет читать или изменять связанную копию.

Доступ по коду не равнозначен системе персональных аккаунтов.

Сервер также не гарантирует сохранность данных при собственной аварии без отдельного резервного копирования его базы.

## 10. Серверная база и безопасность — отложено

> Требования этого раздела применимы только к будущему серверному этапу. Для текущего релиза база находится в браузере; SQLite, VPS и volume не требуются.

### 10.1. Хранение

Для небольшого приложения предлагается SQLite.

База содержит резервные копии игроков и их технические метаданные.

Не хранить серверные данные внутри временной файловой системы контейнера.

Использовать постоянный Docker volume.

### 10.2. Безопасность API

Обязательные меры:

- HTTPS.
- Проверка секретного кода.
- Валидация входящих данных.
- Ограничение размера запросов.
- Ограничение частоты запросов.
- Защита от перебора кодов.
- Защита от массового создания записей.
- Отсутствие секретов в клиентском коде.
- Отсутствие секретов в URL.
- Отсутствие публичного доступа напрямую к файлу базы.
- Отсутствие открытого внешнего порта базы данных.

Поскольку приложение публичное, отдельно предусмотреть ограничения нагрузки и количества создаваемых резервных копий.

### 10.3. Серверные резервные копии

Создать отдельный процесс регулярного резервирования SQLite.

Требования:

1. Создавать согласованные копии базы с использованием безопасного для SQLite метода.
2. Хранить как минимум одну копию вне основного VPS.
3. Ограничить доступ к резервным копиям.
4. Проверять возможность восстановления базы.
5. Контролировать ошибки резервирования.
6. Не удалять резервные копии только из-за пересоздания контейнера.
7. Настроить понятную политику хранения копий.

Конкретную частоту и срок хранения определить в эксплуатационной конфигурации.

**Docker volume не заменяет настоящую резервную копию.**

## 11. PWA и офлайн-режим

### 11.1. Установка

Приложение должно поддерживать установку на главный экран совместимых смартфонов.

Предусмотреть:

- Web App Manifest.
- Название приложения.
- Иконки.
- Standalone-режим.
- Корректный стартовый адрес.
- HTTPS.
- Service Worker.

### 11.2. Офлайн-режим

После первоначальной загрузки и кэширования необходимых ресурсов пользователь должен иметь возможность:

- Открыть приложение.
- Перейти в доступные игровые модули.
- Продолжить партию.
- Выполнять игровые действия.
- Изменять локальные настройки.
- Сохранять прогресс локально.

Игровой процесс, настройки, экспорт и импорт локального файла должны работать без интернета после успешной установки офлайн-ресурсов. Серверных операций в этом релизе нет. Для первой загрузки и получения обновления требуется сеть.

### 11.3. Кэширование

Service Worker должен кэшировать необходимые статические ресурсы приложения.

Не кэшировать ответы API резервных копий как общедоступные статические ресурсы.

Кэш игры и IndexedDB должны иметь независимые жизненные циклы.

Очистка устаревшего кэша при обновлении не должна удалять игровые сохранения.

### 11.4. Обновления

При публикации новой версии:

- Приложение получает новую сборку.
- Совместимые сохранения остаются доступными.
- Миграции выполняются безопасно.
- Во время активной партии не должно происходить принудительного обновления интерфейса с потерей незавершённого хода.

Показывать ненавязчивое предложение применить обновление в подходящий момент. Не выполнять безусловные `skipWaiting`/перезагрузку посреди жеста, хода, импорта или неподтверждённого сохранения. Кэшировать все необходимые части production-сборки, включая отложенные chunks и SVG, чтобы настройки, игра и импорт/экспорт открывались офлайн. При первом запуске различать загрузку страницы и завершённую готовность офлайн-копии.

### 11.5. Особенности устройств

Нужно учитывать, что браузерная версия и установленное PWA могут использовать отдельные локальные хранилища, особенно на iOS.

Разработчик должен протестировать:

- Запуск в Safari.
- Установку на экран Домой.
- Сохранение внутри установленного приложения.
- Повторный запуск PWA.
- Работающую офлайн-копию.
- Экспорт сохранения.
- Восстановление после повторной установки.

Нельзя предполагать, что наличие прогресса в Safari автоматически означает его наличие в установленной игре.

## 12. Развёртывание на GitHub Pages

### 12.1. Окружение

Репозиторий: `https://github.com/dulova/aidagame`.

Целевой стандартный адрес Pages: `https://dulova.github.io/aidagame/`. Это адрес целевой конфигурации; публикация и включение Pages проверяются отдельно. Собственный домен, VPS и Coolify не входят в ближайший релиз.

### 12.2. Статическая сборка и пути

Собрать Vue-приложение Vite в `dist/`; на Pages публиковать только результат сборки. Настроить `base: '/aidagame/'`. Пути JS/CSS, SVG, manifest, start_url, scope и Service Worker должны работать из подкаталога `/aidagame/`. Не привязывать SVG-маски к каталогу исходного CSS; проверить фактические запросы production-сборки.

Не использовать history-маршруты, требующие серверного rewrite, без согласованного решения; для текущих экранов достаточно состояния приложения или hash-навигации. Пользователю не требуется Node.js для запуска опубликованной игры.

### 12.3. Воспроизводимость и CI

Зафиксировать зависимости lock-файлом; CI использует `npm ci`, отдельную проверку TypeScript, unit/integration-тесты, production-сборку и браузерные проверки критических сценариев. Команды фиксируются в package scripts и README после реализации. Тесты не объявлять пройденными только по успешному build.

### 12.4. Контроль публикации

Проверки запускаются в рабочих ветках/PR без публикации. Подготовить workflow публикации Pages из проверенного `dist/`, но не выполнять push, merge, запуск deployment workflow или публикацию без отдельного разрешения пользователя. Учесть, что действующий workflow публикует при push в `main`; любые будущие изменения триггеров явно описать.

### 12.5. Сохранность прогресса

Деплой не очищает IndexedDB и не переименовывает базу. Проверить миграцию и переход со старого Service Worker. Данные привязаны к origin браузера: переход с прежнего домена/localhost на `dulova.github.io` не переносит их автоматически; до смены origin нужен экспорт из прежней установки. Совместимость формата не равнозначна переносу хранилища между доменами. Перед откатом проверить совместимость кода с новой схемой; откат приложения не должен автоматически удалять данные.

## 13. Производительность и качество

### 13.1. Игровой процесс

- Игровые действия рассчитываются локально.
- Отрисовка должна оставаться плавной на обычных смартфонах.
- Перетаскивание не должно зависеть от сетевой задержки.
- Не использовать тяжёлые анимационные библиотеки без необходимости.
- Избегать лишних перерисовок всего интерфейса.
- Состояние игры должно обновляться предсказуемо.

### 13.2. Доступность

- Интерактивные элементы должны иметь достаточные размеры.
- На компьютере должен быть видимый клавиатурный фокус.
- Поддерживать `prefers-reduced-motion`.
- Не допускать случайной прокрутки во время игрового жеста.
- Поддерживать безопасные области экрана смартфона.
- При ошибке локального хранения сохранять доступ к экспорту и сообщать о несохранённых изменениях; конфликтующую запись блокировать до явного разрешения.

### 13.3. Производительность сборки и PWA

Сравнить старую версию и новую production-сборку в одинаковых условиях. Записать версии браузера, устройство/CPU, сеть, viewport и метод измерения; выполнить минимум 5 прогонов холодного старта и повторного офлайн-старта, привести медианы. Не сравнивать Vite dev-сервер со старой production-версией.

Проверить gzip-размер JS/CSS, объём precache, время до готовности меню и игры, задержку ввода, длинные задачи и перетаскивание/очистку на телефоне. Отдельно проверить все отложенные chunks офлайн. Vite/TypeScript, тестовые библиотеки и инструменты анализа не включать в браузерный runtime. Шаблоны Vue компилировать на сборке; не подключать тяжёлую библиотеку интерфейса или анимаций без необходимости.

Согласованные бюджеты релиза 1.2.0: JS+CSS первой загрузки не более 150 КиБ после gzip; суммарные файлы обязательного precache не более 1 МиБ без сжатия. В одинаковом мобильном профиле медиана готовности к вводу при холодном старте — до 3 с, повторный запуск из кэша — до 1 с. Это цели, а не уже полученные результаты. При превышении представить замеры, причину и исправление; не объявлять производительность принятой без проверки. Профиль и возможность проверки реального iPhone явно указать в отчёте.

### 13.4. Ограничения инфраструктуры

Приложение полностью работает на статическом хостинге. Не вводить backend, Redis, очереди, WebSocket, аккаунты, SSR, аналитику или новые игры в рамках технической миграции. Накопленная статистика всех партий отложена.

## 14. Тестирование

### 14.1. Игровые модули

Каждый игровой модуль обязан иметь собственные тесты правил.

Для Block Puzzle тесты определяются отдельным ТЗ игровой логики.

### 14.2. Приложение

Проверить:

- Навигацию.
- Открытие независимых игр.
- Состояния партий в каталоге.
- Смену темы.
- Сохранение настроек.
- Отсутствие влияния настроек на игровую логику.
- Возврат в меню без потери партии.
- Корректную работу общих диалогов.

### 14.3. Локальные сохранения

Обязательные сценарии:

1. Сохранение после завершённого хода.
2. Восстановление после перезагрузки.
3. Восстановление после закрытия браузера.
4. Независимые сохранения нескольких игр.
5. Отдельное хранение рекорда и его сохранение после новой партии.
6. Смена темы без изменения состояния игры.
7. Ошибка записи в IndexedDB.
8. Повреждённые данные.
9. Миграция старой схемы.
10. Конфликт двух вкладок, включая новую партию, импорт и открытие старой версии базы.
11. Совместимость IndexedDB/localStorage v1 и повторное выполнение миграции.
12. Ошибка записи не выдаётся за успешное сохранение.

### 14.4. Экспорт и импорт

Проверить:

- Экспорт всех игр.
- Корректность JSON.
- Импорт после переустановки.
- Отказ от повреждённого файла.
- Отказ от несовместимой версии.
- Подтверждение замены прогресса.
- Сохранность текущих данных при ошибке импорта.
- Чтение прежнего формата бэкапа v1 и нового контейнера v2.
- Отмена и полный откат при ошибке записи рекорда/настроек.
- Полное восстановление более низкого рекорда из файла без скрытого объединения.
- Конфликт ревизии между предварительным просмотром и подтверждением.
- Экспорт актуального состояния из памяти при отказе записи.

### 14.5. Серверное резервирование — отложено

Не является проверкой ближайшего релиза: сервер отсутствует. При отдельном согласовании серверного этапа восстановить тестовую матрицу по разделам 9–10.

### 14.6. PWA

Проверить:

- Установку на поддерживаемые Android- и iOS-устройства.
- Автономный запуск.
- Сохранение внутри установленной PWA.
- Обновление версии.
- Сохранность прогресса после обновления.
- Работу на компактных экранах.
- Восстановление прогресса после удаления и новой установки приложения.

Последний сценарий считается успешно пройденным только при наличии ранее созданного экспортированного файла. Отдельно проверить путь `/aidagame/`, отсутствие 404 для всех рисунков в превью/слотах/поле/перетаскивании, оба режима всех тем и экспорт/импорт без сети. Серверной копии в этом релизе нет.

## 16. Критерии готовности ближайшего релиза

1. Используется согласованный Vue 3 + Vite + TypeScript; проверки типов, тесты и production build проходят.
2. Игровые правила сохранены, кроме явно согласованного удаления обязательной небольшой фигуры из обычной генерации. Новая тройка имеет допустимый ход, если он возможен; невозможность хода корректно завершает партию без бесконечной генерации.
3. Шесть тем с двумя режимами и шесть согласованных рисунков работают во всех состояниях без ошибок путей.
4. Рекорд хранится отдельно; текущая партия, рекорд и настройки не теряются после обновления или миграции v1.
5. Записи и импорт атомарны; ошибки и конфликты вкладок не скрываются. Повреждённый импорт не меняет прежние данные.
6. Кнопки экспорта/импорта находятся внизу настроек. Полное восстановление поддерживает старый и новый форматы, требует предварительного просмотра и подтверждения.
7. PWA работает из `/aidagame/`, офлайн и после управляемого обновления. Удаление локальных данных восстанавливается только из заранее сохранённого пользователем файла.
8. Статичная подложка поля неподвижна; анимируются отдельные блоки. Очистка логически одновременна, визуально выполняется коротким каскадом; `prefers-reduced-motion` учитывается и в ожиданиях управления.
9. Представлен отчёт сравнения производительности и соответствия утверждённым бюджетам; непроверенные устройства перечислены.
10. Вёрстка проверена на 390×844, 320×568 и 1440×900, в Safari и установленной PWA при наличии реального устройства.
11. Готова матрица «требование → реализация → тест/проверка → результат». Сервер и накопленные счётчики не выдаются за реализованные.
12. Публикация подготовлена, но не выполняется без отдельного разрешения пользователя.

Основной принцип: игровая логика, оболочка, визуальное оформление и хранение имеют отдельные зоны ответственности. Сохранённый бренд и совместимость данных обязательны.
