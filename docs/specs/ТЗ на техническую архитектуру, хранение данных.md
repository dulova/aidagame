# ТЗ на техническую архитектуру, хранение данных и развёртывание

как реализовать уже спроектированное приложение, а не заново описывать, где расположены кнопки и как выглядят игровые блоки.

**Тип продукта:** публичное веб-приложение с поддержкой PWA

**Инфраструктура:** собственный VPS, Coolify

**Приоритет:** корректность, простота сопровождения, сохранность прогресса и расширяемость

## 1. Назначение документа

Документ определяет техническую реализацию приложения «Муроблоки».

Он устанавливает:

- Технологический стек.
- Архитектуру общей оболочки.
- Принципы подключения игровых модулей.
- Управление состоянием приложения.
- Структуру и жизненный цикл игровых сохранений.
- Резервное копирование и восстановление прогресса.
- Технические требования к PWA.
- Организацию серверного компонента.
- Требования к безопасности, производительности и качеству.
- Порядок сборки, публикации и обновления.

Документ не переопределяет игровые механики, пользовательские сценарии и визуальный дизайн.

### 1.1. Связанные документы

При разработке использовать:

1. «Муроблоки — ТЗ на экраны и вайрфреймы».
2. «Муроблоки — ТЗ на визуальный дизайн приложения».
3. «Block Puzzle — игровая логика и механики v1.1».
4. Отдельные ТЗ будущих игровых модулей.

В случае противоречий не менять требования самостоятельно. Проблему необходимо зафиксировать и согласовать.

## 2. Продуктовая и техническая модель

«Муроблоки» — общедоступное приложение с независимыми казуальными головоломками.

Пользователь открывает сайт в браузере либо устанавливает его на главный экран смартфона как PWA.

### 2.1. Принципы

- Приложение доступно без обязательной регистрации.
- Публичный доступ к игровому коду и интерфейсу разрешён.
- Каждому устройству доступен собственный локальный прогресс.
- Для игрового процесса не требуется постоянное подключение к серверу.
- Разные игровые модули имеют независимые партии и рекорды.
- Общие настройки оформления используются на уровне приложения.
- Потеря сетевого соединения не должна прерывать активную игру.
- Новые игровые модули подключаются без существенной переработки существующих.

### 2.2. Состав игровых модулей

Предусмотреть архитектуру для:

- `block-puzzle` — головоломка с размещением фигур.
- `2048` — головоломка с объединением числовых плиток.
- `tap-match` — будущая головоломка на сопоставление элементов.

**Реализация механик 2048 и Tap Match не входит в текущий технический объём, пока для них не согласованы отдельные ТЗ.**

Первым полностью реализуемым модулем является Block Puzzle.

Общая оболочка должна поддерживать каталог игр, независимо от количества готовых модулей.

В продуктовой версии не должны запускаться неготовые игры или экраны с имитацией игрового процесса.

## 3. Технологический стек

### 3.1. Клиентское приложение

Предлагаемый стек:

| Компонент | Технология |
| --- | --- |
| Язык | TypeScript |
| Сборка | Vite |
| UI-компоненты | Vue 3 — рекомендуемый вариант |
| Стили | CSS с переменными и дизайн-токенами |
| PWA | vite-plugin-pwa |
| Локальная база | IndexedDB |
| Доступ к IndexedDB | idb или аналогичная лёгкая библиотека |
| Тесты логики | Vitest |
| E2E-тесты | Playwright |
| Контроль версий | Git |

Vue 3 является рекомендацией, а не уже согласованным продуктовым требованием. До начала реализации разработчик должен подтвердить выбор UI-подхода.

Не использовать Next.js, SSR и серверный рендеринг без обоснованной необходимости.

Для первой версии приложение может полностью работать на стороне клиента.

### 3.2. Отрисовка игровых полей

Для Block Puzzle предпочтительно использовать DOM/CSS Grid и Pointer Events.

Причины:

- Поле состоит из небольшого количества дискретных клеток.
- Не требуется физический движок.
- Анимации достаточно простые.
- Можно напрямую применять CSS-темы.
- Удобнее управлять адаптивностью и состояниями элементов.

Canvas допускается, если испытания покажут существенные преимущества.

Технология отрисовки не должна влиять на правила игры.

Другие игровые модули могут использовать иной способ отображения, если это требуется их механикой.

### 3.3. Серверный компонент

Для дополнительного резервного копирования предлагается:

- Node.js с актуальной поддерживаемой LTS-версией.
- TypeScript.
- Минимальный HTTP API.
- SQLite для хранения резервных копий.
- Постоянный Docker volume.
- HTTPS через reverse proxy.

Не создавать полноценную серверную игровую платформу.

Сервер не должен обрабатывать игровые ходы, начислять очки или управлять локальными партиями.

Отвечает за:

- Доступ к IndexedDB.
- Экспорт и импорт JSON.

- Обработку ошибок хранения.
- Версионирование и миграции.

## 5. Контракт игрового модуля

Приложение должно подключать игровые модули через минимальный общий контракт.

### 5.1. Обязательные сведения

Каждый модуль предоставляет:

- `id` — уникальный постоянный идентификатор.
- `name` — название.
- `load` — способ загрузки экрана игры.
- `createInitialState` — создание начального состояния.
- `getStatus` — получение состояния партии для общего меню.
- `validateSave` — проверка корректности сохранения.
- `saveVersion` — версия формата игровых данных.

Дополнительные методы определяются потребностями конкретной игры.

### 5.2. Статусы партии

Общее приложение использует:

- `not_started` — партия отсутствует.
- `active` — партия доступна для продолжения.
- `completed` — партия закончена.

Внутренние состояния вроде перетаскивания, обработки очистки или анимации остаются внутри игрового модуля.

### 5.3. Изоляция модулей

Запрещается:

- Использовать единое состояние поля для всех игр.
- Включать правила Block Puzzle в общую оболочку.
- Привязывать общие настройки к одному игровому модулю.
- Использовать одинаковые ключи сохранений для разных головоломок.

Общие сервисы не должны знать, как устроены внутренние игровые правила.

### 5.4. Подключение новой игры

Для добавления новой головоломки должно быть достаточно:

1. Создать модуль игры.
2. Реализовать его правила и интерфейс.
3. Определить формат сохранения.
4. Зарегистрировать модуль в каталоге.
5. Добавить необходимые тесты.

Добавление модуля не должно требовать изменения правил уже существующих игр.

## 6. Управление состоянием

### 6.1. Уровни состояния

Разделить данные на три категории.

**Общее состояние приложения:**

- Активная цветовая тема.
- Выбранные настройки оформления.
- Текущий экран.
- Состояние общих диалогов.

**Состояние игрового модуля:**

- Текущая партия.
- Счёт.
- Рекорд.
- Внутренняя статистика.
- Игровые данные.

**Состояние инфраструктуры:**

- Состояние локального сохранения.
- Доступность сервера.
- Состояние резервного копирования.
- Дата последней успешной копии.
- Наличие ошибок восстановления.

### 6.2. Требования

- Возврат в меню не сбрасывает игровую партию.
- Смена темы не перезаписывает игровые данные.
- Открытие другого игрового модуля не удаляет предыдущие сохранения.
- Новая партия сбрасывает только данные соответствующей игры.
- Рекорд сохраняется отдельно от текущей партии.
- Временное состояние взаимодействия не обязано сохраняться.

Например, положение фигуры в процессе незавершённого перетаскивания не записывается.

## 7. Локальное хранение данных

### 7.1. Основное хранилище

Использовать IndexedDB.

Локальная база должна хранить прогресс непосредственно на устройстве пользователя.

Не использовать localStorage как основной источник истины для игрового прогресса.

### 7.2. Логическая структура

Предусмотреть хранилища:

| Хранилище | Содержание |
| --- | --- |
| `settings` | Общие настройки приложения |
| `gameSaves` | Снимки состояния партий |
| `gameRecords` | Рекорды и накопленная статистика |
| `backupMetadata` | Служебные данные резервного копирования |
| `metadata` | Версия схемы и технические данные |

Каждая запись игровых данных должна быть связана с `gameId`.

### 7.3. Настройки приложения

Пример структуры:

```json
{
  "schemaVersion": 1,
  "themeId": "light",
  "gameAppearance": {
    "block-puzzle": {
      "patternId": "plain"
    }
  }
}
```

Цветовая тема является общей для приложения.

Рисунки блоков относятся к конкретному игровому модулю, поскольку другие головоломки могут не поддерживать аналогичное оформление.

Восемь тем и шесть наборов рисунков определяются актуальным ТЗ на UI-дизайн.

### 7.4. Сохранение партии

Пример структуры:

```json
{
  "gameId": "block-puzzle",
  "schemaVersion": 1,
  "status": "active",
  "revision": 12,
  "updatedAt": "2026-10-29T12:00:00Z",
  "state": {
    "board": [],
    "availableShapes": [],
    "score": 240,
    "clearedLines": 8
  }
}
```

Содержимое `state` определяется конкретным игровым модулем.

Для Block Puzzle внутри состояния необходимо хранить сведения о визуальной группе занятых клеток.

Не сохранять HEX-цвет каждой клетки. Цвет вычисляется по идентификатору группы и активной теме.

### 7.5. Рекорды

Рекорды и накопленная статистика хранятся отдельно от текущей партии.

При начале новой игры:

- Текущая партия сбрасывается.
- Рекорд сохраняется.
- Общие настройки сохраняются.
- Результаты других головоломок не изменяются.

### 7.6. Момент автосохранения

Сохранение выполняется:

- После каждого успешно завершённого хода.
- После изменения настроек.
- После окончания партии.
- После подтверждённого начала новой партии.
- После изменения накопленной статистики.

Состояние должно сохраняться как согласованный снимок.

Нельзя записывать частично завершённый ход, при котором поле уже изменилось, но очки или доступные фигуры ещё не обновлены.

### 7.7. Атомарность

Операции сохранения взаимосвязанных данных должны использовать транзакции IndexedDB.

При ошибке записи не должно возникать частично сохранённого состояния.

Если запись не удалась:

1. Не сообщать пользователю об успешном сохранении.
2. Сохранить актуальное состояние в памяти, пока приложение открыто.
3. Показать ненавязчивое предупреждение.
4. Предложить повторную попытку сохранения или экспорт, если это возможно.

### 7.8. Несколько вкладок

Предусмотреть защиту от конфликтов при открытии одного приложения в нескольких вкладках.

Рекомендуется:

- Использовать ревизии сохранений.
- Перед записью проверять ожидаемую ревизию.
- Предотвращать тихую перезапись более свежего состояния старым.
- Уведомлять другие вкладки через BroadcastChannel, если API доступен.

Если текущая вкладка обнаружила более новую версию партии, нельзя незаметно заменить её собственным устаревшим состоянием.

### 7.9. Устойчивость хранения

При поддержке браузером допускается запрос постоянного хранения через `navigator.storage.persist()`.

Успех запроса нельзя считать гарантированным.

Данные могут быть потеряны при удалении приложения, очистке хранилища или отдельных действиях системы.

**Локальное хранение не является резервным копированием.**

## 8. Экспорт и импорт сохранений

Экспорт и импорт являются обязательными общими функциями приложения.

Они должны охватывать данные всех поддерживаемых игровых модулей.

### 8.1. Экспорт

Пользователь может вручную скачать резервную копию в формате JSON.

Рекомендуемое имя:

`muroblocks-backup-YYYY-MM-DD.json`

Файл содержит:

- Идентификатор приложения.
- Версию формата экспорта.
- Дату создания.
- Общие настройки.
- Состояния партий.
- Рекорды и статистику всех доступных игр.

Пример внешней структуры:

```json
{
  "appId": "muroblocks",
  "exportVersion": 1,
  "exportedAt": "2026-10-29T12:00:00Z",
  "settings": {},
  "games": {
    "block-puzzle": {
      "saveVersion": 1,
      "save": {},
      "records": {}
    }
  }
}
```

Это структура контейнера экспорта, а не окончательная модель конкретного игрового состояния.

### 8.2. Исключения из экспорта

В файл не включать:

- Секретный код доступа к серверной копии.
- Серверные ключи.
- Внутренние токены.
- Служебные данные установки, не необходимые для восстановления.
- Чувствительные конфигурационные параметры инфраструктуры.

### 8.3. Импорт

При выборе файла приложение должно:

1. Прочитать файл.
2. Проверить его формат.
3. Проверить идентификатор приложения.
4. Проверить поддерживаемую версию экспорта.
5. Проверить данные каждого игрового модуля.
6. Показать, какие данные будут восстановлены.
7. Предупредить о замене существующих сохранений.
8. Запросить подтверждение.
9. Выполнить восстановление согласованно, без частичной записи.

Не перезаписывать текущий прогресс без явного подтверждения пользователя.

Перед импортом желательно автоматически подготовить резервную копию текущего состояния, доступную для восстановления.

### 8.4. Ошибки импорта

Обрабатывать:

- Неподходящий файл.
- Повреждённый JSON.
- Неизвестное приложение.
- Неподдерживаемую версию сохранения.
- Некорректные игровые данные.
- Ошибку записи в IndexedDB.

При ошибке существующие корректные сохранения должны остаться нетронутыми.

### 8.5. Совместимость

Новые версии приложения должны поддерживать миграцию известных старых схем сохранения.

Неизвестные более новые версии нельзя загружать с попыткой угадать их структуру.

Если миграция невозможна, необходимо безопасно отказаться от импорта и объяснить причину.

## 9. Необязательное серверное резервное копирование

**Назначение:** восстановление прогресса после удаления установленного PWA, повреждения устройства или потери локальных данных.

Серверное резервирование не заменяет локальное хранение и не является обязательным для начала игры.

### 9.1. Принцип работы

Пользователь играет без регистрации.

При желании он включает резервное копирование в настройках.

Приложение создаёт отдельную запись резервной копии на сервере и выдаёт секретный код восстановления.

Пользователь сохраняет код вне приложения.

После включения:

- Основной игровой прогресс остаётся в IndexedDB.
- При наличии интернета приложение отправляет обновлённый снимок данных на сервер.
- Если интернет отсутствует, игра продолжает работать локально.
- При возвращении интернета приложение пытается передать актуальные изменения.

### 9.2. Код восстановления

Код является секретом, подтверждающим право доступа к конкретной резервной копии.

Требования:

- Генерируется криптографически стойким способом.
- Не создаётся из имени пользователя, даты или простого числа.
- Имеет достаточную случайность — не менее 128 бит.
- Используется для чтения и обновления только своей записи.
- Не хранится на сервере в открытом виде.
- Не включается в URL.
- Не попадает в журналы запросов.
- Передаётся только через HTTPS.
- Не включается в обычный JSON-экспорт.

На сервере хранить производный проверочный идентификатор или хеш секретного кода.

При утере кода без сохранившейся авторизованной установки восстановление серверной копии не гарантируется.

### 9.3. Состав серверной записи

Предусмотреть:

- Уникальный ID резервной копии.
- Проверочный хеш секретного кода.
- Версию схемы.
- Ревизию данных.
- Дату создания.
- Дату последнего изменения.
- JSON-снимок прогресса.
- Служебную информацию для предотвращения конфликтов.

Не собирать имена, телефоны и email игроков для работы резервного копирования.

### 9.4. API

Предусмотреть минимальные операции:

**Создание резервной копии**

- Создать запись.
- Сформировать секрет восстановления.
- Вернуть информацию для сохранения на устройстве.

**Получение копии**

- Проверить секрет.
- Вернуть сохранённые данные и текущую ревизию.

**Обновление копии**

- Проверить секрет.
- Проверить ожидаемую ревизию.
- Валидировать формат данных.
- Сохранить новое состояние.

**Удаление копии**

- Проверить секрет.
- Удалить связанные данные по явному запросу пользователя.

Конкретные HTTP-маршруты и формат запросов зафиксировать в API-контракте перед реализацией.

### 9.5. Автоматическая отправка

Отправлять копию после изменений локальных данных с небольшой задержкой, объединяющей несколько последовательных операций.

Не создавать отдельный сетевой запрос на каждый кадр, движение фигуры или промежуточную анимацию.

Допустимая стратегия:

- Сохранить ход локально немедленно.
- Отметить данные как требующие резервирования.
- Через небольшую задержку попытаться передать актуальный снимок.
- При ошибке сети повторить попытку позже.

Резервирование не должно блокировать игровой процесс.

### 9.6. Состояние резервного копирования

Приложение должно различать:

- `disabled` — резервирование не включено.
- `pending` — есть локальные изменения, ещё не отправленные на сервер.
- `syncing` — выполняется отправка.
- `backed_up` — последняя копия успешно сохранена.
- `error` — ошибка соединения или сервера.
- `conflict` — обнаружено несовпадение ревизий.

Нельзя показывать «Прогресс сохранён на сервере», если последний запрос завершился ошибкой.

### 9.7. Восстановление

При вводе кода восстановления:

1. Проверить наличие соединения.
2. Выполнить запрос к серверу.
3. Проверить полученные данные.
4. Показать информацию о доступной копии.
5. Предупредить о возможной замене локального прогресса.
6. Запросить подтверждение.
7. Восстановить данные в IndexedDB.
8. Обновить приложение без потери восстановленных данных.

После успешного восстановления пользователь может продолжить игру с последнего успешно зарезервированного состояния.

### 9.8. Несколько устройств

**В этой версии резервное копирование не является полноценной синхронизацией нескольких устройств.**

Предполагается один основной источник изменений для одной серверной копии.

Если два устройства используют один код и пытаются обновлять одну копию, сервер должен предотвращать тихую перезапись более новых данных устаревшими.

Для этого использовать контроль ревизий.

При конфликте:

- Остановить автоматическую перезапись.
- Сообщить пользователю.
- Сохранить локальные данные обоих устройств.
- Не объединять игровые партии автоматически.
- Предложить явное восстановление или выбор версии после согласования соответствующего интерфейса.

Полноценная двусторонняя синхронизация не входит в текущую версию.

### 9.9. Ограничения

Код восстановления фактически является ключом доступа к сохранению.

Если он станет известен постороннему, тот потенциально сможет читать или изменять связанную копию.

Доступ по коду не равнозначен системе персональных аккаунтов.

Сервер также не гарантирует сохранность данных при собственной аварии без отдельного резервного копирования его базы.

## 10. Серверная база и безопасность

### 10.1. Хранение

Для небольшого приложения предлагается SQLite.

База содержит резервные копии игроков и их технические метаданные.

Не хранить серверные данные внутри временной файловой системы контейнера.

Использовать постоянный Docker volume.

### 10.2. Безопасность API

Обязательные меры:

- HTTPS.
- Проверка секретного кода.
- Валидация входящих данных.
- Ограничение размера запросов.
- Ограничение частоты запросов.
- Защита от перебора кодов.
- Защита от массового создания записей.
- Отсутствие секретов в клиентском коде.
- Отсутствие секретов в URL.
- Отсутствие публичного доступа напрямую к файлу базы.
- Отсутствие открытого внешнего порта базы данных.

Поскольку приложение публичное, отдельно предусмотреть ограничения нагрузки и количества создаваемых резервных копий.

### 10.3. Серверные резервные копии

Создать отдельный процесс регулярного резервирования SQLite.

Требования:

1. Создавать согласованные копии базы с использованием безопасного для SQLite метода.
2. Хранить как минимум одну копию вне основного VPS.
3. Ограничить доступ к резервным копиям.
4. Проверять возможность восстановления базы.
5. Контролировать ошибки резервирования.
6. Не удалять резервные копии только из-за пересоздания контейнера.
7. Настроить понятную политику хранения копий.

Конкретную частоту и срок хранения определить в эксплуатационной конфигурации.

**Docker volume не заменяет настоящую резервную копию.**

## 11. PWA и офлайн-режим

### 11.1. Установка

Приложение должно поддерживать установку на главный экран совместимых смартфонов.

Предусмотреть:

- Web App Manifest.
- Название приложения.
- Иконки.
- Standalone-режим.
- Корректный стартовый адрес.
- HTTPS.
- Service Worker.

### 11.2. Офлайн-режим

После первоначальной загрузки и кэширования необходимых ресурсов пользователь должен иметь возможность:

- Открыть приложение.
- Перейти в доступные игровые модули.
- Продолжить партию.
- Выполнять игровые действия.
- Изменять локальные настройки.
- Сохранять прогресс локально.

Без интернета не работают операции, которым необходим VPS, включая получение и отправку серверной резервной копии.

### 11.3. Кэширование

Service Worker должен кэшировать необходимые статические ресурсы приложения.

Не кэшировать ответы API резервных копий как общедоступные статические ресурсы.

Кэш игры и IndexedDB должны иметь независимые жизненные циклы.

Очистка устаревшего кэша при обновлении не должна удалять игровые сохранения.

### 11.4. Обновления

При публикации новой версии:

- Приложение получает новую сборку.
- Совместимые сохранения остаются доступными.
- Миграции выполняются безопасно.
- Во время активной партии не должно происходить принудительного обновления интерфейса с потерей незавершённого хода.

Рекомендуется показывать ненавязчивое предложение применить обновление в подходящий момент.

### 11.5. Особенности устройств

Нужно учитывать, что браузерная версия и установленное PWA могут использовать отдельные локальные хранилища, особенно на iOS.

Разработчик должен протестировать:

- Запуск в Safari.
- Установку на экран Домой.
- Сохранение внутри установленного приложения.
- Повторный запуск PWA.
- Работающую офлайн-копию.
- Экспорт сохранения.
- Восстановление после повторной установки.

Нельзя предполагать, что наличие прогресса в Safari автоматически означает его наличие в установленной игре.

## 12. Развёртывание

### 12.1. Окружение

Основной домен:

`https://muroblock.aidanastya.ru`

Размещение:

- Собственный VPS.
- Coolify.
- HTTPS.
- Git-репозиторий с исходным кодом.

### 12.2. Состав развёртывания

**Клиентская часть**

- Собирается в статические файлы.
- Обслуживается веб-сервером.
- Не требует запущенного Node.js для выполнения игровых ходов.

**API резервного копирования**

- Работает как отдельный серверный процесс.
- Имеет доступ к постоянному хранилищу SQLite.
- Публикуется через reverse proxy.

Желательно использовать единый домен:

- `/` — клиентское приложение.
- `/api/` — API резервного копирования.

Конкретная конфигурация маршрутизации определяется при настройке инфраструктуры.

### 12.3. Сборка

Сборка должна быть воспроизводимой.

Обязательные требования:

- Зафиксированные зависимости.
- Отсутствие секретов в Git.
- Проверка TypeScript.
- Автоматические тесты.
- Production-сборка.
- Проверка критических сценариев после публикации.

### 12.4. Деплой

Рекомендуемый процесс:

1. Изменения вносятся в отдельную Git-ветку.
2. Проходят проверки.
3. Сливаются в основную ветку.
4. Создаётся production-сборка.
5. Coolify публикует обновление.
6. Выполняется проверка работоспособности.
7. При ошибке доступен возврат к предыдущему релизу.

При откате кода необходимо учитывать совместимость схем сохранений и серверной базы.

### 12.5. Сохранность данных при деплое

Обновление контейнера не должно уничтожать:

- SQLite.
- Серверные резервные копии.
- Метаданные доступа к копиям.
- Секреты инфраструктуры.

Перед потенциально несовместимыми миграциями серверной базы обязательно создавать резервную копию.

## 13. Производительность и качество

### 13.1. Игровой процесс

- Игровые действия рассчитываются локально.
- Отрисовка должна оставаться плавной на обычных смартфонах.
- Перетаскивание не должно зависеть от сетевой задержки.
- Не использовать тяжёлые анимационные библиотеки без необходимости.
- Избегать лишних перерисовок всего интерфейса.
- Состояние игры должно обновляться предсказуемо.

### 13.2. Доступность

- Интерактивные элементы должны иметь достаточные размеры.
- На компьютере должен быть видимый клавиатурный фокус.
- Поддерживать `prefers-reduced-motion`.
- Не допускать случайной прокрутки во время игрового жеста.
- Поддерживать безопасные области экрана смартфона.
- Не блокировать действия из-за недоступности сервера резервирования.

### 13.3. Ограничения инфраструктуры

Приложение должно быть пригодно для размещения на небольшом VPS.

Не использовать без необходимости:

- Отдельную систему очередей.
- Redis.
- Микросервисную архитектуру.
- Тяжёлую аналитическую инфраструктуру.
- Постоянные WebSocket-соединения.
- Серверный игровой движок.

Сложность инфраструктуры должна соответствовать реальной нагрузке.

## 16. Критерии готовности

Техническое решение считается выполненным в согласованном объёме, если:

16. Серверные данные защищены от обычного пересоздания контейнеров.
